# 后端技术方案设计

## 1. 明确范围和依据

- 从已确认的需求、验收场景和变更边界出发，明确本次做什么、不做什么。按需读取目标模块的 `AGENTS.md`、已有契约、代码、数据定义和运行约束。
- 标注现状证据与待决策项。依赖接口、约束或历史数据不明确时，标出缺口及其影响；不要把假设写成现状。
- 沿用项目已有的接口形式、架构边界、术语和文档位置。没有证据时，不预设语言、框架、数据库、目录结构或工具。

## 2. 写最小可评审方案

| 内容 | 必须答清的问题 |
| --- | --- |
| 接口与边界 | 哪个模块负责什么？调用双方是谁？写清变更后的输入、输出、错误语义和兼容性；不改接口时注明。 |
| 数据与状态 | 谁拥有数据、谁可写？哪些约束或状态迁移必须成立？涉及存量时说明迁移、部署顺序、验证与回滚或前向修复。 |
| 决策与关键风险 | 写明关键取舍及理由。按实际风险检查权限、事务、并发、幂等、外部依赖失败或可观测性，无关项不展开。 |
| 验收与待确认项 | 将需求映射到可观察结果，至少说明常见成功场景和关键失败场景。列出未决问题、阻塞范围和下一步验证方式。 |

复杂变更再补顺序图、数据流或状态表。对跨团队契约、难以回滚的变更等重要决策，比较至少一个可行替代方案；简单变更用短文档即可。

## 3. 评审与交接

- 使用项目已有的设计文档位置；由 `design-manager` 调用时，按其要求记录方案索引 ID 并同步索引。
- 交付设计文档、关键决策、需要拍板的问题和验收入口。需要组织评审时交给 `tech-design-review-template`，方案确认后再交给 `task-split`。
- 未确认的契约、迁移策略或职责边界标注为未冻结。本技能不写实现代码，也不执行迁移。
