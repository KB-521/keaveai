---
name: phase-router
description: 所有用户请求的入口，负责分析意图、判断复杂度并路由到合适的代理。
---

## 核心机制

```
用户输入 → 分析意图 → 判断复杂度 → 路由到代理 → 执行
↑                                               |
└────────────────────── 循环 ────────────────────┘
```

## 步骤 1：分析意图

| 意图类型 | 关键词/信号 | 路由到 |
|---------|-------------|--------|
| 新产品/功能/需求审查 | "创建", "做一个", "帮我建" | requirement-manager |
| 需求拆分/排期规划 | "拆分", "分阶段", "里程碑", "批次" | requirement-manager |
| 设计问题 | "架构", "怎么设计", "API", "技术方案", "先出方案", "API契约", "设计评审" | design-manager |
| 实现、缺陷修复或重构 | "实现", "修复", "改一下", "bug" | 主会话先通过 `task-delivery` 第 0 节判断门禁 |

## 步骤 2：判断复杂度

| 等级 | 信号 | 路径 |
|------|------|------|
| **简单** | 验收明确、局部、易回退且可针对性验证的低风险单项改动 | → 按 `task-delivery` 第 0 节判断；符合简易路径则由主会话执行 |
| **中等** | 新功能、API 变更 | → 需求 → 设计 → 实现 |
| **复杂** | 新模块/系统/产品 | → 完整流程，逐步与用户确认 |

## 步骤 3：路由与执行

下列路线中的 implementation-executor 都由主会话在 `common/task-delivery/SKILL.md` 内委派，不能自行在共享工作区编码。需求、设计及只读评审可独立完成，不自动进入实现。

### 简单任务（门禁通过后直接执行）
```
用户: "修复登录按钮的样式"
→ 先检查风险和仓库规则 → 主会话直接修改、精简、自审和验证 → 按授权和仓库规则交付
→ 若仅合并需要守门员，保留已验证的修复并按仓库流程送审，不因角色缺失而阻塞实现
```

### 中等任务（标准流程）
```
用户: "添加用户注册功能"
→ requirement-manager (细化需求)
→ design-manager (设计方案)
→ implementation-executor (开发)
```

### 中等任务（设计后拆分）
```
用户: "把技术方案拆成可实施批次"
→ requirement-manager (task-split 拆分父子需求与依赖)
→ implementation-executor (按批次闭环开发)
```

### 复杂任务（完整流程 + 用户确认）
```
用户: "帮我做一个电商系统"
→ requirement-manager (拆解模块) → 用户确认
→ design-manager (整体架构) → 用户确认
→ design-manager (接口设计) → 用户确认
→ implementation-executor (逐模块开发) → 用户确认
→ 循环直到完成
```

## 输出格式

```markdown
## 意图分析
- **输入**：[用户消息]
- **意图**：[新需求/补充/设计/修复/记录]
- **复杂度**：[简单/中等/复杂]

## 路由决策
→ [代理名称]
→ 原因：[原因说明]

## 已执行操作
- [x] 已路由到 [代理]
```
