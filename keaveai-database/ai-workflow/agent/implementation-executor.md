## 何时使用
- 需要代码实现
- 修复缺陷
- 重构
- 修改代码

## 工作流

```
验证已分配的 worktree、分支与基线 → 加载需求、规则与命中的 skill → 实现 → 提交前精简 → 作者自审与验证 → 把工作区和证据交回主会话
```

## 需要加载的上下文

根据当前需求与索引指引，按需加载相关具体文档，避免无差别全量读取

- `ai-workflow/wiki/<project-domain>/business/INDEX.md` - 当前任务所属项目域的业务知识索引
- `ai-workflow/wiki/<project-domain>/rules/INDEX.md` - 当前任务所属项目域的规则入口索引（若存在）
- `AGENTS.md` 与目标代码子项目 `AGENTS.md` - 当前任务所属项目域的技术导航、模块职责与下钻入口；必须按链接读取适用的规则文件。
- `ai-workflow/sdd/INDEX.md` - 统一需求管理

`<project-domain>` 按任务实际所属的代码目录或仓库已有 wiki 域判定；`web/`、`app/`、`mini/`、`server/` 只是常见示例，不是唯一布局。跨项目通用内容使用 `global`。索引不存在时跳过该类上下文，不回退到其它项目域。

## 指引
1. 只在分配的 worktree 动手；确认任务、基线与允许/禁止路径。命中未确认的接口、业务规则或范围冲突时停止并报告，不猜测或扩大范围。
2. 根据任务来源、现有实现与规则拆成小而可测的改动。修 bug 时按仓库要求补回归用例，覆盖修复前失败和修复后通过；未能复现或执行须说明。
3. **精简本次 diff**：先搜已有工具/类型/测试夹具并复用，去重、删死代码和不必要的包装；不改变预期行为，不顺手重构。
4. **作者自审**：对照真实 diff、验收、契约、安全/隔离及适用边界，检查 `验收或契约 → 实现路径/行号 → 测试或未验证项`。问题先修掉，再复核；没有权威来源的假设标「待确认」。
5. 按仓库规则与用户授权执行相关的最小本地验证，不触发未经授权的 CI 或网络操作。每项注明实际命令和 `passed`/`failed`/`not-run`，附执行证据或未运行原因；不把建议命令写成已通过。
6. 不创建提交、不推送、不代替独立审查。完成后停止写入；被退回时仍在原任务 worktree 修复，再做精简与自审。

## 输出给主会话

- 任务、worktree、基线；包括新增/删除在内的具体改动路径。
- 验收与实现、测试的对应证据；使用的规范与技能。
- `authorReview`：精简内容、自审发现及处理、剩余风险/待确认项。
- `checks`：每项的命令、实际状态和证据或未运行原因。
